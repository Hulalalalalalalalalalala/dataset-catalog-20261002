# Dataset Catalog

A local registry of dataset fields and direct dependencies, requiring Python 3.10+ and no third-party packages. It records descriptions and schemas, not the dataset contents.

`python3 dataset_catalog.py describe orders` reads the included sample catalog. `python3 dataset_catalog.py dependencies daily_totals` returns the registered orders entry; queries are direct-only, not transitive. `python3 dataset_catalog.py impact orders` reports every registered dataset reachable downstream of `orders`; pass `--max-depth` (a positive decimal integer) to limit how many dependency edges are traversed. Each item holds only `dataset` (the same full record `describe` prints), `distance` (the fewest dependency edges from the start) and `path` (the id sequence from the start to that downstream dataset, both ends included, ties between equally short paths choosing the lexicographically smallest id sequence); the start is never listed, every downstream dataset appears once, and results are sorted by distance and then dataset id, with catalog key and dependency array order never affecting distance, path or ordering. Argument formats are validated before the catalog is read: a start id not matching the ID rule, or a depth that is not a positive integer, raises `ValueError`, as does an unregistered start. Before any result is produced the whole catalog is validated with `preview`'s metadata rules — a non-object top level, an invalid descriptor, a record key disagreeing with its id, a duplicate or missing dependency, a self dependency or a cycle anywhere raises `ValueError` with no partial result, even beyond the depth limit, outside the queried subgraph or when the start has no downstream at all; a registered leaf returns `[]`. A missing catalog file or one containing `{}` is an empty catalog, an unreadable file raises `OSError`, invalid JSON raises `json.JSONDecodeError`, and the read-only query never writes files, creates directories or reads dataset contents; CLI failures print JSON containing `error` and exit 2, success prints the result JSON and exits 0. `python3 dataset_catalog.py upstream daily_totals` is the mirror query along `depends_on`: it lists the direct and indirect upstream datasets of `daily_totals` (never the start itself), each item holding only `dataset` (the same full record `describe` prints), `distance` (the fewest dependency edges from the start) and `path` (the id sequence from the start to that upstream, both ends included). Every upstream appears once, sorted by distance and then by dataset id; ties between equally short paths choose the lexicographically smallest id sequence, and catalog or dependency ordering never changes the result. `--max-depth` (a positive decimal integer) keeps only records whose shortest distance stays within the limit, and omitting it returns the whole upstream closure; a registered dataset with no upstream yields `[]`. The start and its entire upstream closure are validated like a self-contained catalog — an invalid start id or depth, an unregistered start, a non-object catalog, and inside the closure an invalid descriptor, a record key disagreeing with its id, a duplicate or missing dependency, a self dependency or a cycle all raise `ValueError` with no partial result, and a depth limit never hides errors in farther upstream records, while records and relations outside the closure are ignored. Argument formats are validated before the catalog is read; a missing catalog file or one containing `{}` is an empty catalog, an unreadable file raises `OSError` and invalid JSON raises `json.JSONDecodeError`. The query never modifies or creates files or directories and never reads dataset contents. `python3 dataset_catalog.py common-upstream --id orders --id daily_totals` finds the sources shared by several datasets: it returns an array sorted by source id, each item holding only `dataset` (the full record `describe` returns) and `targets` (every distinct target id, sorted, each with only `id`, `distance` and `path` — the fewest dependency edges from that target to the source and the id sequence from the target to the source, both ends included; ties choose the lexicographically smallest id sequence). Each target participates together with every upstream dataset reachable through `depends_on`, and a target itself is distance 0 with a one-id path. A source is shared only when every target can reach it, and a candidate that another shared source depends on directly or indirectly is omitted, so multiple mutually independent common sources are all kept rather than picking one by summed distance; when nothing is shared the output is `[]`. For the sample catalog, querying `orders` and `daily_totals` returns only `orders`, with distances 0 and 1. Repeat `--id` to name targets (duplicates merge; at least two distinct valid ids are required) and input order never changes the result. Argument formats are validated before the catalog is read: a non-list argument, a member not matching the ID rule, fewer than two distinct targets or an unregistered target raises `ValueError`; a non-object catalog top level or, inside any target's full upstream closure, an invalid descriptor, a record key disagreeing with its id, a duplicate or missing dependency, a self dependency or a cycle raises `ValueError` with no partial result, while records outside the target closures are ignored. A missing catalog file is treated as an empty catalog (so all targets are unknown), an unreadable file raises `OSError`, invalid JSON raises `json.JSONDecodeError`, and the read-only query never creates or modifies files or directories or reads dataset contents; CLI failures print JSON containing `error` and exit 2, success prints the result JSON and exits 0. `python3 dataset_catalog.py between orders daily_totals` reports the directed dependency chain from `SOURCE` to `TARGET` along `depends_on` (B depending on A is the edge A→B): it prints exactly `{"datasets": [...], "edges": [...]}`. `datasets` collects every full record — the same object `describe` prints — that lies on at least one directed source-to-target path, including every connecting branch and paths of different lengths, sorted by id and without duplicates; branches leading off the chain and isolated nodes are never pulled in, and complete paths are not enumerated. `edges` lists only edges that sit on such a path, each item holding just `source` and `target` (the two ids), sorted by source and then target and deduplicated. The same id given for both ends, when registered, returns that one record and an empty `edges` array; two registered ends with no source-to-target path return two empty arrays, so the reversed direction `daily_totals` to `orders` is empty. The whole catalog uses `preview`'s metadata normalization and graph validation: a non-object top level, an invalid descriptor, a record key disagreeing with its id, a duplicate or missing dependency, a self dependency or a cycle anywhere — even outside the chain — raises `ValueError` with no partial result. Both endpoint formats are validated as existing id-rule strings before the catalog is read, and an unregistered end raises `ValueError`; a missing catalog file or one containing `{}` is an empty catalog so both ends are unknown. An unreadable file raises `OSError`, invalid JSON raises `json.JSONDecodeError`, and the read-only query never writes files, creates directories or reads dataset contents; CLI failures print JSON containing only `error` and exit 2, success prints the result JSON and exits 0, and catalog key or dependency array order never changes the result. For the sample catalog, `between orders daily_totals` returns both records plus the single edge `orders`→`daily_totals`. `python3 dataset_catalog.py critical SOURCE TARGET` prints a JSON array of the datasets that every directed path from SOURCE to TARGET passes through, with `between`'s edge direction (B's `depends_on` containing A is the edge A→B) and judging only the registered relations, never field lineage: each item is the same full record `describe` prints, every dataset appears once, the array is sorted by id, and no path set is enumerated. When a source-to-target path exists both ends are included; the same registered id for both ends returns just that one record, two registered ends with no source-to-target path return `[]`, and the reversed direction is judged by its own reachability. Every path counts regardless of length, so a merge point shared by all branches is included only while no longer bypassing path avoids it, and unrelated branches and isolated records never appear. Both endpoint formats are validated as existing id-rule strings before the catalog is read, and an unregistered end raises `ValueError`; a missing catalog file or one containing `{}` is an empty catalog so both ends are unknown. The whole catalog is normalized and graph-validated with `preview`'s rules — a non-object top level, an invalid descriptor, a record key disagreeing with its id, a duplicate or missing dependency, a self dependency or a cycle anywhere raises `ValueError` with no partial result, even outside the queried paths or when both ends are the same. An unreadable file raises `OSError`, invalid JSON raises `json.JSONDecodeError`, and the read-only query never writes files, creates directories or reads dataset contents; CLI failures print JSON containing only `error` and exit 2, success prints the result JSON and exits 0, and catalog key or dependency-array order never changes the result. For the sample catalog, `critical orders daily_totals` returns both records. `python3 dataset_catalog.py export --id daily_totals` writes `{"datasets": [...]}` containing the selected datasets together with every upstream dataset reachable through `depends_on`; repeat `--id` to select more (duplicates merge), or omit it to export the whole catalog. Records are ordered dependencies first, breaking ties by id; exporting never modifies the catalog, and the output can be fed back to `register` entry by entry to rebuild the selected subset offline. `python3 dataset_catalog.py export-csv --id daily_totals` prints the same selection as a field-level CSV data dictionary for viewing datasets and fields together in a table: the fixed header is `dataset_id,description,owner,tags,depends_on,field_name,field_type`, every field gets one row and the dataset metadata is repeated across that dataset's rows. It reuses `--catalog`, repeatable `--id` and `export`'s selection semantics (no `--id` means everything, duplicate ids merge, the full upstream closure is included and input order never matters); datasets stay ordered dependencies first and fields keep registration order. A missing owner is an empty cell while missing tags prints `[]`; `tags` and `depends_on` are compact JSON arrays that preserve Chinese characters, with tags in stored order and dependencies sorted by id. Rows end with `\n` and cells containing commas, double quotes or newlines are double quoted with inner quotes doubled; newlines inside field names and descriptions are kept verbatim. An empty catalog or an empty selection prints only the terminated header. Selection arguments are validated before the catalog is read (a non-list argument, a non-string or invalid id, or an unknown id raises `ValueError`); a missing catalog file is treated as an empty catalog while a non-object top level raises `ValueError`, and the selected closure is normalized and graph-validated like `upstream` (invalid metadata, key/id mismatches, duplicate or missing dependencies, self dependencies and cycles raise `ValueError` with no partial output, while records outside the closure are ignored). An unreadable file raises `OSError`, invalid JSON raises `json.JSONDecodeError`, and failures print JSON containing only `error` and exit 2; success prints the CSV directly and exits 0. `python3 dataset_catalog.py import FILE` imports a whole export-shaped bundle (`{"datasets": [...]}`) in one batch into the catalog selected by `--catalog`; dependencies may point at already registered datasets or at other datasets in the same batch, descriptors may appear in any order, and only metadata is registered — dataset contents are never read. Any validation failure rejects the whole batch, leaves the catalog file untouched and never creates a missing file or its parent directories; CLI errors are JSON with exit code 2. `python3 dataset_catalog.py diff FILE` performs a read-only comparison: the catalog selected by `--catalog` is the before state and the `{"datasets": [...]}` snapshot in FILE is the complete after state (a partial export still represents the whole after catalog and is not padded with current records, and records matching by id are compared directly without import's existing-id conflict rule). It prints `{"added": [...], "removed": [...], "changed": [...]}`, each array sorted by dataset id; `added` and `removed` hold full normalized records found only on one side, while each `changed` item holds `id`, `before`, `after` and a lexicographically sorted `changed_keys` list, and unchanged same-id records are omitted (empty arrays are still returned). Snapshot descriptors follow the same normalization rules as registration, so description conversion, field filtering, dependency sorting, tag cleaning and owner cleaning apply, unsaved extra properties and object key order are ignored, and tag spelling/order changes — including omitting `tags` versus `tags: []` — and owner changes (adding, removing, or changing the cleaned spelling, but not surrounding whitespace alone) count as changes, while dataset or dependency ordering alone do not. The snapshot is validated as a self-contained catalog: dependencies may use forward references but must stay inside the snapshot, and a non-object snapshot, a missing or non-array `datasets` key, an invalid descriptor, a duplicate id, a duplicate or missing dependency, a self dependency or a cycle raises `ValueError` with no partial diff; an empty snapshot means the after state has no datasets, while a missing catalog file or one containing `{}` means an empty before state. The comparison never mutates the passed bundle, the catalog file or the snapshot file, never creates files or directories, never reads dataset contents, and an unreadable file, invalid JSON or failed validation prints JSON containing `error` and exits 2. `python3 dataset_catalog.py preview FILE` is a read-only change-impact preview with the same before/after snapshot semantics as `diff`: it prints `{"diff": {...}, "affected": [...]}`, where `diff` is exactly the object `diff` prints and `affected` lists every downstream dataset reached from a change source. Added and removed records and every `changed` record are change sources — a description-only, tags-only or owner-only change propagates just like any other change — and when the diff is empty `affected` is `[]`. Each affected item (sorted by dataset id) holds only `id` and `causes`; a dataset appears once per side on which any change source reaches it along downstream edges, but a change source is never listed solely because it itself changed (it may still appear when another source reaches it). `causes` is sorted by source id and each cause holds only the source `id` plus `before` and `after`, the shortest propagation explanation on that side (positive edge `distance` and a `path` including source and target; ties choose the lexicographically smallest id sequence), or `null` when the source or target is absent or unreachable on that side; a cause with both sides `null` is omitted. The two sides are queried independently — a path valid only after the change is never stitched onto a before path — so a removed source can still affect retained or removed datasets in `before`, while an added source propagates only in `after`. Preview applies the snapshot validation of `diff` and additionally validates the current catalog's dependency graph: invalid descriptors, duplicate ids, duplicate or missing dependencies, self dependencies and cycles all raise `ValueError` with no partial result; a missing catalog file or `{}` is an empty catalog and an empty snapshot deletes every record. Preview never mutates its inputs, files or directories, never reads dataset contents, and its output does not depend on input ordering; file, JSON or validation failures print JSON containing `error` and exit 2. `python3 dataset_catalog.py schema-diff FILE` is a read-only field-change review with the same before/after snapshot semantics as `diff` and `preview`: the catalog selected by `--catalog` is the before state and the complete `{"datasets": [...]}` snapshot in FILE is the after state (a partial export is still the whole after catalog and is not padded, an empty snapshot means no datasets remain, and a missing catalog file or one containing `{}` means an empty before state). It prints `{"changes": [...]}`, sorted by dataset id and containing only records whose fields changed; records without a field change are omitted and when nothing changed it prints `{"changes": []}`. Each item holds only `id`, `added_fields`, `removed_fields`, `type_changes` and `breaking`: the first two arrays hold `name`/`type` pairs and `type_changes` holds `name`/`before`/`after` pairs giving the field name and its types on each side, and all three arrays are sorted by field name in Unicode code-point order (empty arrays are still present). Every field of a newly added dataset counts as added and every field of a deleted dataset counts as removed; same-named fields pair by exact name with no whitespace stripping or case folding, so a rename appears as the old field removed and the new field added, and changes limited to field order, description, tags, owner or dependencies produce no item. `breaking` is this feature's fixed review verdict — `true` whenever a field is removed or a type changes other than integer to number (the only non-breaking type change), and `false` otherwise, so a plain integer-to-number widening alone is not breaking. Both sides use `preview`'s normalization and full dependency-graph validation, so invalid descriptors, duplicate ids, duplicate or missing dependencies, self dependencies and cycles raise `ValueError` with no partial result, even when only other metadata would change; an unreadable file raises `OSError` and invalid JSON raises `json.JSONDecodeError`, and every such CLI failure prints JSON containing `error` and exits 2. The command never mutates the passed bundle or any file, never creates directories and never reads dataset contents. `python3 dataset_catalog.py relation-diff FILE` is a read-only transitive dependency review with the same before/after snapshot semantics as `diff`, `preview` and `schema-diff`: the catalog selected by `--catalog` is the before state and the complete `{"datasets": [...]}` snapshot in FILE is the after state (a partial export is still the whole after catalog and is not padded, an empty snapshot deletes every record, and a missing catalog file or one containing `{}` is an empty before state). It prints exactly `{"added": [...], "removed": [...], "changed": [...]}` comparing the reachable endpoint pairs of the two dependency graphs, with edges directed like `between` (B depending on A is the relation A→B). Every distinct reachable source→target pair participates at most once, and each item holds only `source`, `target`, `before` and `after`; `before` and `after` are each `null` or an object holding only `distance` (the fewest dependency edges from source to target on that side) and `path` (the id sequence including both ends, ties between equally short paths choosing the lexicographically smallest id sequence). A pair reachable only after the change is `added` with `before: null`, a pair reachable only before is `removed` with `after: null`, and a pair reachable on both sides whose `distance` or `path` differs is `changed`; every other pair is omitted, so field, description, tag or owner changes, alternative-path changes that keep the same shortest explanation, and added or removed isolated records produce no item, and deleting a middle record reports the lost relation between its former ends. The two sides are queried independently — no path mixes states — and the arrays are sorted by `source` and then `target`, so input ordering never changes the result; with no relation change the output is three empty arrays. Both sides are normalized and validated as full dependency graphs with `preview`'s rules even when no relation changes: a non-object catalog or snapshot, a missing or non-array `datasets` key, an invalid descriptor, a catalog key disagreeing with its id, a duplicate id, a duplicate or missing dependency, a self dependency or a cycle all raise `ValueError` with no partial result, an unreadable file raises `OSError` and invalid JSON raises `json.JSONDecodeError`, and every CLI failure prints JSON containing `error` and exits 2 while success prints the result JSON and exits 0. The command never mutates the passed bundle or any file, never creates directories and never reads dataset contents. `python3 dataset_catalog.py apply FILE` commits the `{"datasets": [...]}` snapshot in FILE as the complete new state of the catalog selected by `--catalog`: records matching by id are replaced, new ids are added, records absent from the snapshot are removed (a partial export still represents the whole target catalog and is not padded with current records), and an empty snapshot clears the catalog. It prints the same `{"added": [...], "removed": [...], "changed": [...]}` object `diff` would have printed before the commit. The snapshot follows `diff`'s normalization and validation rules and the current catalog is validated with `preview`'s rules; any validation failure rejects the whole apply, leaves the catalog file untouched and never creates a missing file or its parent directories. The commit is all-or-nothing: when there are differences the full set of normalized records is saved atomically in the existing storage format (creating parent directories as needed), a save failure raises `OSError` with the original file contents preserved and a previously missing file still absent, and when there is no difference nothing is written or created. Pass `--expected FILE` to declare the catalog state the change was based on: FILE holds a `{"datasets": [...]}` snapshot that is validated and normalized exactly like the target snapshot and compared against the current catalog by dataset id (dataset order, object key order, unsaved properties and dependency order are ignored, while field order, tag retention/spelling/order and cleaned owner spelling count); unless the two match, the apply is rejected with `catalog does not match expected snapshot` — even when the target equals the current state — and an empty expected snapshot matches only an empty catalog. A `null` expected file is an invalid snapshot. Only metadata is handled — dataset contents are never read — and after a successful apply every query and export immediately reflects the new state. An unreadable file, invalid JSON, failed validation or a failed save prints JSON containing `error` and exits 2. `python3 dataset_catalog.py merge FILE` incrementally merges the `{"datasets": [...]}` bundle in FILE into the catalog selected by `--catalog` (other top-level keys are ignored): each listed dataset is added when its id is new and fully replaces the same-id record otherwise — omitting `owner` or `tags` removes the old values and omitting `depends_on` stores an empty array — while records the bundle does not list are kept and nothing is ever deleted. It prints the same `{"added": [...], "removed": [...], "changed": [...]}` object `diff` prints, computed between the full catalog before and after the merge, so `removed` is always empty. Descriptors follow registration's normalization and validation, dependencies may name existing records or other records in the same batch in any order including forward references, and batch order never changes the result. The whole current catalog and the merged dependency graph are validated before anything is written — an invalid descriptor, a duplicate id in the batch, a catalog key disagreeing with its id, a duplicate or missing dependency, a self dependency or a cycle anywhere, even in records the bundle does not touch, rejects the whole merge with `ValueError` semantics and leaves the file untouched. An empty batch or a merge with no normalized difference prints three empty arrays without writing a file or creating directories; otherwise the merged state is committed atomically once in the existing storage format. A missing catalog file is treated as an empty catalog, invalid JSON raises a JSON error, and failures print JSON containing `error` and exit 2 while success prints the result JSON and exits 0. `python3 dataset_catalog.py remove --id orders --cascade` removes the datasets named by repeated `--id` options from the catalog selected by `--catalog` — duplicates merge, option order never changes the result, and omitting `--id` means an empty selection. It prints the same `{"added": [...], "removed": [...], "changed": [...]}` object `apply` prints, with `added` and `changed` always empty and `removed` holding the full normalized records of everything deleted, sorted by id. Without `--cascade` only the selected records are removed, and the whole request is rejected with `ValueError` semantics while any dataset outside the selection still depends on a removed record directly or transitively — dependency edges are never rewritten; selecting every downstream dataset explicitly is allowed. With `--cascade` the selection plus every dataset reachable downstream of it is removed (a shared downstream dataset is deleted once) while upstream and unrelated records are kept, so removing `orders` from the sample catalog is rejected by default, cascades to both records with `--cascade`, and removing `daily_totals` alone keeps `orders`. `identifiers` must be a list of id-rule strings and `cascade` a boolean, argument formats are validated before the catalog is read, an unregistered id raises `ValueError`, and the input list is never mutated. Every request normalizes and validates the whole current catalog with `preview`'s rules — a non-object top level, an invalid descriptor, a key disagreeing with its id, a duplicate or missing dependency, a self dependency or a cycle anywhere raises `ValueError` even outside the delete set, and an empty selection still validates but prints three empty arrays without writing a file or creating directories. Deleting every record saves `{}`, which later queries and exports treat as an empty catalog; any deletion commits all-or-nothing, leaving the original file bytes untouched on failure, and a missing catalog file or parent directory is never created. Only local metadata is touched, never dataset contents. Failures print JSON containing only `error` and exit 2; success prints the result JSON and exits 0. `python3 dataset_catalog.py search "daily amount"` performs a read-only keyword search over dataset ids, descriptions and field names (dependency ids and field type text are not searched); the query is optional and `--field-type string|integer|number|boolean` restricts results to datasets having at least one field of that type. `--tag TAG` (repeatable, one tag per flag) restricts results to datasets carrying every given tag. `--owner OWNER` restricts results to datasets whose `owner` string matches the given value in full after Unicode casefold (surrounding Unicode whitespace is stripped first); records without an owner never match an owner filter, and the owner value is not searched by keywords. `--upstream-of ID` limits the search to that start dataset and every dataset reachable as a direct or indirect upstream along `depends_on` (the start itself included, each merge node searched once): for the sample catalog `search amount --upstream-of daily_totals` returns only `orders`, while `search total --upstream-of orders` returns `[]`; the start need not match the keywords for its upstream to be searched. Keywords and the field-type, tag and owner filters keep their existing semantics and all apply together inside that range, with results sorted by dataset id, catalog key and dependency-array order never changing the result, and an omitted flag keeping the catalog-wide search. The `upstream_of` argument must be `None` or an id-rule string (an empty string, a non-string, an illegal id or an unregistered start raises `ValueError`), checked before the catalog is read; when a range is given the catalog top level must be an object and the start together with its complete upstream closure is validated with `upstream`'s rules — invalid metadata, key/id mismatches, duplicate or missing dependencies, self dependencies and cycles raise `ValueError` with no partial result even when the failing record would be filtered out, while records and relations outside the closure are ignored. A missing catalog file or `{}` is an empty catalog so the start is unregistered, an unreadable file raises `OSError`, invalid JSON raises `json.JSONDecodeError`, and the read-only query never writes files, creates directories or reads dataset contents; CLI failures print JSON containing only `error` and exit 2, success prints the result JSON and exits 0. `python3 dataset_catalog.py reconcile BASE INCOMING` previews a read-only three-way reconcile: BASE and INCOMING are complete `{"datasets":[...]}` snapshot files (absent records do not exist) aligned with the current catalog by id, comparing whole normalized records with `diff`'s equality rules. A record equal to the base takes the incoming version, a record whose incoming version equals the base keeps the current version, identical current and incoming versions are adopted, and everything else — different additions, a deletion opposing a modification, or two different modifications, even of different attributes — is a conflict that is never merged field by field. The result holds only `bundle`, `diff` and `conflicts`: with conflicts the first two are null and `conflicts` lists each conflicting id sorted by id, each item holding only `id`, `base`, `current` and `incoming` (null for a record missing on that side, the full normalized record otherwise); without conflicts `conflicts` is `[]`, `bundle` is the apply-ready candidate snapshot with datasets ordered dependencies first like `export`, and `diff` compares the current catalog with the candidate in the usual structure. All three states are validated with `preview`'s metadata and dependency-graph rules before any result, and the merged candidate graph is validated again — a merge-induced missing dependency or cycle raises `ValueError` with no partial result; the preview never writes files, creates directories or reads dataset contents, input ordering never affects the result, and failures print JSON containing only `error` and exit 2. The two sample descriptors are `samples/orders.json` and `samples/daily.json`.

To create a separate catalog, run `python3 dataset_catalog.py --catalog .state/catalog.json register samples/orders.json`, then register `samples/daily.json` in that same catalog. IDs must start with a lowercase letter and contain lowercase letters, digits, underscores or hyphens. Each dataset needs unique field names and field types string, integer, number or boolean. Dependencies must already be registered; registration cannot overwrite an existing ID. This append-only registration order prevents new entries from forming dependency cycles. Registration itself stays append-only with no per-record update or delete — individual records are added or replaced through `merge`, and wholesale replacement or removal happens only by applying a complete snapshot with `apply` — and there is no file ingestion command. A descriptor may also carry an optional `tags` list of strings: each tag is stripped of surrounding Unicode whitespace, must be nonempty, and duplicates are merged by Unicode casefold keeping the first spelling and order. Passing `"tags": []` stores an empty list; omitting the key stores no tags at all. A non-list value, a non-string member or an empty-after-strip tag raises `ValueError` and leaves the catalog untouched. A descriptor may also carry an optional `owner` string naming the single responsible owner: surrounding Unicode whitespace is stripped and the result must be nonempty, after which the cleaned value is stored as given, preserving original casing and internal whitespace. Omitting the key stores no `owner` at all; `null` or any non-string value and an empty-after-strip string raise `ValueError` and leave the catalog untouched.

`DatasetCatalog.register`, `describe` and `dependencies` expose the same API; `DatasetCatalog.impact(identifier, max_depth=None)` returns the downstream list (each item holds only the full `dataset` record `describe` returns, its shortest `distance` and the lexicographically smallest shortest `path` including both ends; the start is excluded, every downstream dataset appears once, and results sort by distance then dataset id). `identifier` must be a string matching the ID rule and `max_depth` must be `None` or a non-boolean positive integer, both validated before the catalog is read; an unregistered start raises `ValueError` (a missing catalog file or `{}` is an empty catalog). The entire catalog is validated with `preview_bundle`'s rules before any result — a non-object top level, invalid descriptors, key/id mismatches, duplicate or missing dependencies, self dependencies and cycles all raise `ValueError` with no partial result, even beyond the depth limit or outside the queried subgraph — and a registered leaf returns `[]`. The query never writes or creates files. `DatasetCatalog.upstream(identifier, max_depth=None)` is the mirror query along `depends_on`: it returns the direct and indirect upstream datasets of `identifier` (excluding the start), each item holding only `dataset` (the same full record `describe` returns), `distance` (the fewest dependency edges) and `path` (the id sequence from the start to that upstream, both ends included), sorted by distance and then dataset id, with ties between equally short paths choosing the lexicographically smallest id sequence; `max_depth` must be `None` or a non-boolean positive integer and keeps only records within that shortest distance. The start and its full upstream closure are validated (invalid start id or depth, unregistered start, non-object catalog, and in-closure invalid descriptors, key/id mismatches, duplicate or missing dependencies, self dependencies and cycles all raise `ValueError` with no partial result, and a depth limit never skips farther-upstream validation), records outside the closure are ignored, argument formats are checked before the catalog is read, and the query never writes or creates files. `DatasetCatalog.common_upstream(identifiers)` finds the nearest common upstream sources of two or more datasets: `identifiers` must be a list of strings matching the ID rule; duplicates merge, input order never affects the result, and a non-list, an invalid member or fewer than two distinct ids raises `ValueError` before the catalog is read, as does an unregistered id (a missing catalog file or `{}` is an empty catalog). It returns a list sorted by source id, each item holding only `dataset` (the full record `describe` returns) and `targets`; `targets` contains every distinct target sorted by id, each with only `id`, `distance` (the fewest dependency edges from that target to the source, zero when the target is itself the source) and `path` (the id sequence from the target to the source, both ends included, choosing the lexicographically smallest sequence among shortest paths). Every target participates together with its full reachable upstream closure. A node is a candidate only when every target can reach it; a candidate that another candidate depends on directly or indirectly is not returned, so all mutually independent common sources are kept regardless of distance totals, and when no node is shared the result is `[]`. The targets and their complete upstream closures are validated like a self-contained catalog — a non-object top level, an invalid descriptor, a key/id mismatch, a duplicate or missing dependency, a self dependency or a cycle anywhere in that combined range raises `ValueError` with no partial result, while records outside the range are ignored.
