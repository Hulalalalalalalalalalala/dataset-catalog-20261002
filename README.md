# Dataset Catalog

A local registry of dataset fields and direct dependencies, requiring Python 3.10+ and no third-party packages. It records descriptions and schemas, not the dataset contents.

`python3 dataset_catalog.py describe orders` reads the included sample catalog. `python3 dataset_catalog.py dependencies daily_totals` returns the registered orders entry; queries are direct-only, not transitive. `python3 dataset_catalog.py impact orders` reports every registered dataset reachable downstream of `orders`, each with its shortest distance and propagation path; pass `--max-depth` (a positive integer) to limit how many dependency edges are traversed. `python3 dataset_catalog.py export --id daily_totals` writes `{"datasets": [...]}` containing the selected datasets together with every upstream dataset reachable through `depends_on`; repeat `--id` to select more (duplicates merge), or omit it to export the whole catalog. Records are ordered dependencies first, breaking ties by id; exporting never modifies the catalog, and the output can be fed back to `register` entry by entry to rebuild the selected subset offline. `python3 dataset_catalog.py import FILE` imports a whole export-shaped bundle (`{"datasets": [...]}`) in one batch into the catalog selected by `--catalog`; dependencies may point at already registered datasets or at other datasets in the same batch, descriptors may appear in any order, and only metadata is registered — dataset contents are never read. Any validation failure rejects the whole batch, leaves the catalog file untouched and never creates a missing file or its parent directories; CLI errors are JSON with exit code 2. `python3 dataset_catalog.py search "daily amount"` performs a read-only keyword search over dataset ids, descriptions and field names (dependency ids and field type text are not searched); the query is optional and `--field-type string|integer|number|boolean` restricts results to datasets having at least one field of that type. `--tag TAG` (repeatable, one tag per flag) restricts results to datasets carrying every given tag. The two sample descriptors are `samples/orders.json` and `samples/daily.json`.

To create a separate catalog, run `python3 dataset_catalog.py --catalog .state/catalog.json register samples/orders.json`, then register `samples/daily.json` in that same catalog. IDs must start with a lowercase letter and contain lowercase letters, digits, underscores or hyphens. Each dataset needs unique field names and field types string, integer, number or boolean. Dependencies must already be registered; registration cannot overwrite an existing ID. This append-only registration order prevents new entries from forming dependency cycles. There is no schema evolution, deletion or file ingestion command. A descriptor may also carry an optional `tags` list of strings: each tag is stripped of surrounding Unicode whitespace, must be nonempty, and duplicates are merged by Unicode casefold keeping the first spelling and order. Passing `"tags": []` stores an empty list; omitting the key stores no tags at all. A non-list value, a non-string member or an empty-after-strip tag raises `ValueError` and leaves the catalog untouched.

`DatasetCatalog.register`, `describe` and `dependencies` expose the same API; `DatasetCatalog.impact(identifier, max_depth=None)` returns the downstream list (each item holds the full `dataset` record, its shortest `distance` and the lexicographically smallest shortest `path`; `max_depth` must be `None` or a positive integer). `DatasetCatalog.export(identifiers=None)` returns `{"datasets": [...]}`: `None` exports everything, `[]` an empty array, otherwise a list of valid registered ids (strings matching the ID rule); duplicates merge and input order never affects the result. The result covers the selected datasets plus their full upstream closure along `depends_on`, each record appearing once, ordered with dependencies before dependents and lexicographically smallest id among currently-ready datasets. A missing dependency or a dependency cycle inside the selected closure raises `ValueError`; relations outside the selection are ignored. `DatasetCatalog.import_bundle(bundle)` accepts an object with the same `{"datasets": [...]}` shape `export` produces (any other top-level keys are ignored) and registers every descriptor in one transaction: each descriptor follows the same field, description, tags and duplicate-dependency rules as `register`, while dependencies may name either existing ids or other ids in the batch, in any order and including forward references. Duplicate ids inside the batch, ids already registered (even with identical content, which is never overwritten), unknown dependencies, self dependencies and batch-internal cycles, as well as a non-object bundle, a missing or non-array `datasets` key, and any descriptor that would fail `register`, all raise `ValueError` before anything is saved — the catalog file keeps its original contents and a missing catalog file (or its parent directories) is never created. On success it returns `{"datasets": [...]}` holding only the newly added, fully normalized records, ordered dependencies first with lexicographically-smallest-id tie-breaking, so input order never changes the result; `{"datasets": []}` returns an empty array and never writes; the passed-in object is never mutated. Afterwards the new records are immediately visible through `describe`, `dependencies`, `search`, `impact` and `export` with their existing semantics. Plain `register` still accepts exactly one descriptor whose dependencies are all already registered. `DatasetCatalog.diff_bundle(bundle)` is a read-only comparison between the current catalog (before) and a `{"datasets": [...]}` snapshot (after); `python3 dataset_catalog.py diff FILE` runs it against the catalog selected by `--catalog`. The snapshot is treated as the complete catalog — even one produced by a partial export — so nothing is merged in from current records, and same-named datasets are compared directly rather than rejected as already registered. The result holds only `added`, `removed` and `changed` arrays, each sorted by dataset id: `added` lists the fully normalized records found only in the snapshot, `removed` the full records found only in the catalog, and each `changed` item holds `id`, the full `before` and `after` records, and `changed_keys`, the differing attribute names in alphabetical order (identical records are omitted, and empty categories stay as empty arrays). Comparison applies the same description conversion, field retention, dependency sorting and tag cleanup as registration, ignoring unstored extra attributes and object key order; field order, tag spelling and order, and omitting `tags` versus `tags: []` all count as changes, while the order of datasets in the snapshot or of ids inside `depends_on` does not. Snapshot descriptors follow the usual validation rules except that dependencies may only reference other datasets inside the snapshot, in any order and including forward references; a non-object bundle, a missing or non-array `datasets` key, an invalid descriptor, duplicate ids, duplicate or missing dependencies, self dependencies and cycles all raise `ValueError` and yield no partial diff. An empty snapshot means the after-side has no datasets, and a missing catalog file or one containing `{}` is treated as empty. Diffing never modifies the passed bundle, the catalog file or the snapshot file, never creates missing files or directories, and never reads dataset contents; CLI errors are JSON with exit code 2. `DatasetCatalog.search(query="", field_type=None)` is read-only and returns a list sorted by dataset id; each item holds the same full record as `describe` under `dataset` and `matched_fields`, the field names hit by any query word in original field order without duplicates (empty when no field is hit or the query is empty). The query is split on Unicode whitespace, duplicate words do not change the result, and matching is literal substring matching after Unicode casefold — no regex or wildcards; every word must hit the same dataset, possibly across its id, description and different field names. An empty or whitespace-only query imposes no keyword restriction; when `field_type` is one of string, integer, number or boolean the dataset must have at least one field of that type while keywords still search every field name. A non-string query, or a `field_type` other than `None` and the four supported types, raises `ValueError` — arguments are validated before the catalog is read, so a missing or empty catalog still yields `[]` and never creates a file. `DatasetCatalog.search(query="", field_type=None, tags=None)` also accepts `tags`: `None` or `[]` imposes no tag restriction, while a nonempty list requires the dataset to carry every listed tag. Tags follow the same type, stripping and dedup rules as registration, are validated before the catalog is read, and match whole tags by Unicode casefold only — no word splitting, substring, regex or wildcard matching. Records registered before tags existed are treated as having no tags and are never rewritten by a search. Keyword, field-type and tag conditions all apply together; keywords still search only the original scopes and `matched_fields` still reflects keyword hits only. CLI errors are JSON and exit 2. Run `python3 -B -m unittest -v` for persistence, dependency validation and CLI tests.
